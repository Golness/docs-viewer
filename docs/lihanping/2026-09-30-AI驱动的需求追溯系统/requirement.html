方案总览

将现有 docs-viewer 插件从纯文档浏览器升级为 AI 辅助的需求追溯系统。核心设计原则：

  • 不自动执行：所有 AI 操作通过按钮手动触发
  • 三区分离：操作栏（左）、文档浏览（中）、需求追溯（右）
  • AI 辅助：通过 DSH ctx.llm 调用模型
  • Prompt 可配置：分析 Prompt 支持自定义

可行性分析

#需求点结论DSH API 依据风险/备注
1.1目录命名规范✅ 可行纯约定，无需 DSH API 支持。服务端用 fs.mkdirSync 创建目录无
1.2目录自动解析✅ 可行ctx.workspaceRegistry.list() 获取所有 workspace 路径，fs.readdir() 递归扫描 docs 目录，正则 /^(\d{4}-\d{2}-\d{2})-(.+)$/ 解析目录名现有插件已实现类似逻辑（FileListPanel），可复用
1.3文档类型识别✅ 可行纯文件名匹配，path.extname() 判断扩展名，文件名前缀判断类型（requirement/design/cr）无
1.4.meta.json 规范✅ 可行JSON Schema 定义 + fs.writeFile 写入。可用 ctx.storageDomain 做 schema 验证，但直接 JSON 读写更简单建议用 JSON Schema 做运行时校验，防止 AI 输出格式错误
1.5JSON Schema 校验✅ 可行使用 @deepseek-ai/schemastery 定义 Schema，AI 输出后先校验再写入。校验失败时记录警告日志并写入默认值需定义完整的 Schema 结构，包含必填字段和类型约束

需求点清单

#需求点描述优先级
3.1搜索框支持输入关键词搜索功能点、字段、标签P1
3.2搜索类型筛选可选择搜索范围：全部 / 功能点 / 字段 / 标签P1
3.3搜索结果卡片每个匹配需求显示为卡片，包含标题、开发者、日期、文档数、摘要、标签P1
3.4时间线展示点击搜索结果展开时间线，按日期排列所有事件节点P1
3.5时间线节点类型区分四种节点：📋 需求文档、📐 技术方案、🔍 CR 反馈、✅ 上线发布P1
3.6跨需求字段关联搜索字段时展示所有涉及该字段的需求列表，揭示字段变更历史P2
3.7未分析提示如果需求没有 .meta.json，显示提示引导用户去操作指引区点击分析P1
3.8AI 辅助模糊查询与精确搜索平级的搜索模式，用户可主动选择「精确搜索」或「AI 智能搜索」。AI 搜索调用 ctx.llm 对查询词进行语义理解和模糊匹配，适用于模糊描述、同义词、跨领域关联等场景P2
3.9搜索结果计数搜索结果顶部显示匹配数量统计（如 "找到 3 个需求涉及此字段"），帮助用户快速了解匹配规模P1
3.10搜索结果源码引用搜索结果卡片内显示匹配文档的原文片段引用（如 "requirement.md (L15-L30)" + 引号包裹的原文摘录），帮助用户定位具体上下文P1
3.11需求规模标签搜索结果卡片标题旁显示需求规模彩色标签（"大需求" 黄色 / "小需求" 绿色），与 .meta.json 的 type 字段对应P1
3.12AI 搜索加载状态AI 智能搜索调用时显示加载动画和提示文字（如 "AI 正在分析语义…"），避免用户误以为页面无响应P2
3.13AI 匹配原因说明每个 AI 搜索结果附带 "💡 AI 分析" 原因说明卡片，解释该需求与查询词的语义关联P2
3.14搜索模式切换控件搜索栏上方提供精确搜索/AI 智能搜索的 segmented control 切换按钮组，当前选中模式高亮P2
3.15时间线节点描述时间线每个节点除标题外，还显示描述文字（如 "并行处理方案，预估优化到 10min"），提供更详细的事件上下文P1

可行性分析

#需求点结论DSH API 依据风险/备注
3.1搜索框✅ 可行客户端 React.createElement('input') 渲染搜索框，fetch('/docs-viewer/search?q=xxx') 调用服务端搜索接口需实现服务端搜索接口，基于 search-index.json 全文检索
3.2搜索类型筛选✅ 可行客户端用 useState 管理筛选状态，fetch('/docs-viewer/search?type=feature|field|tag') 传递筛选参数服务端需在索引中区分 featureIndex、fieldIndex、tagIndex 三类
3.3搜索结果卡片✅ 可行客户端用 React.createElement 渲染卡片组件，数据从 search-index.json 的 requirements 数组读取无
3.4时间线展示✅ 可行客户端渲染时间线组件，数据从 .meta.json 的 timeline 字段读取，按日期排序需确保 AI 生成的 timeline 格式统一
3.5时间线节点类型✅ 可行纯前端逻辑，根据 .meta.json 中 timeline 节点的 type 字段（requirement/design/cr/release）渲染不同图标和颜色需在 Prompt 中明确要求 AI 输出节点类型
3.6跨需求字段关联✅ 可行服务端从 search-index.json 的 fieldIndex 读取字段关联的需求 ID 列表，返回所有涉及该字段的需求依赖 AI 准确提取字段信息
3.7未分析提示✅ 可行服务端在返回需求列表时标记 hasMeta: boolean，客户端根据此字段显示提示 UI无
3.8AI 辅助模糊查询✅ 可行搜索栏增加模式切换（精确/AI），服务端 ctx.llm.stream() 接收查询词 + 索引摘要，AI 返回语义匹配的需求 ID 列表及匹配度评分。客户端调用 POST /docs-viewer/ai-search需控制 Prompt 长度（只传索引摘要，不传全文），避免超出 context window；AI 搜索响应时间较长（3-10秒），需显示加载状态
3.9搜索结果计数✅ 可行服务端搜索 API 返回 total 字段，客户端在结果列表顶部渲染 "找到 N 个需求涉及此字段/功能点"无
3.10搜索结果源码引用✅ 可行服务端在索引中存储每个需求文档的原文片段（截取关键段落），搜索命中时返回 snippets: [{ file, lines, text }]，客户端渲染为引用块需在 rebuild-index 时额外存储文档摘要片段，增加索引体积
3.11需求规模标签✅ 可行服务端返回的搜索结果中包含 type 字段（large/medium/small），客户端根据 type 渲染不同颜色的 badge（large→黄色"大需求"，small→绿色"小需求"）无
3.12AI 搜索加载状态✅ 可行客户端在发起 AI 搜索请求时设置 loading=true，显示加载动画和提示文字，响应完成后隐藏需处理请求超时（建议 30 秒超时后显示重试按钮）
3.13AI 匹配原因说明✅ 可行服务端 AI 搜索返回的每个结果包含 reason 字段，客户端渲染为 "💡 AI 分析" 提示卡片依赖 AI 输出质量，Prompt 中需明确要求输出匹配原因
3.14搜索模式切换控件✅ 可行客户端用 useState 管理 searchMode（'exact' | 'ai'），渲染 segmented control 按钮组，切换时重新触发搜索无
3.15时间线节点描述✅ 可行服务端返回的 timeline 节点包含 description 字段，客户端在节点标题下方渲染描述文字需在 Prompt 中要求 AI 输出 description
3.16跨需求字段关联面板✅ 可行服务端 GET /docs-viewer/fields/:field 从 fieldIndex 查找关联需求列表，返回每个需求的日期、标题、变更说明，客户端渲染为关联面板依赖 AI 准确提取字段变更说明

#需求点结论DSH API 依据风险/备注
5.1ctx.llm 集成✅ 可行inject: ['llm'] 声明依赖，ctx.llm.stream({ provider, model, messages, temperature, maxTokens }) 调用模型。返回 AsyncIterable<StreamChunk>，用 BlockAssembler 收集文本块需处理 finish.reason === 'error' 和 'max-tokens' 两种异常结束
5.2文档读取✅ 可行ctx.workspaceRegistry.list() 获取 workspace 路径，fs.readdir() 扫描目录，fs.readFile() 读取 .md 文件内容拼接为 Prompt大文档可能超出 context window，需截断或摘要
5.3结构化输出✅ 可行Prompt 中明确要求返回 JSON，maxTokens: 4000 确保输出完整。用 BlockAssembler 收集文本后 JSON.parseAI 输出格式不稳定，需三级容错（见 5.4）
5.4JSON 解析容错✅ 可行纯代码逻辑：1) 尝试 JSON.parse 直接解析；2) 正则提取 ```json...``` 代码块；3) 降级返回默认值 { type: 'unknown', summary: '', features: [], fields: [], tags: [], timeline: [] }建议加 JSON Schema 校验（可用 @deepseek-ai/schemastery）
5.5.meta.json 写入✅ 可行fs.writeFile(join(reqDir, '.meta.json'), JSON.stringify(meta, null, 2))需原子写入（先写临时文件再 rename），防止写入中断导致文件损坏
5.6Prompt 可配置✅ 可行readFile('config.json') 读取 ai.prompts.analyze 字段，作为 system prompt 传入 ctx.llm.stream()需内置默认 Prompt，用户未配置时使用默认值
5.7Provider/Model 可配置✅ 可行config.json 中 ai.provider 和 ai.model 传入 ctx.llm.stream() 的 provider/model 参数需校验 provider/model 是否存在，可用 ctx.llm.listProviders() 和 ctx.llm.listModels(provider)
5.8分析进度日志✅ 可行服务端在 analyze 函数中每个关键步骤调用 logProgress(message)，将日志推送到内存数组，客户端通过 SSE 或轮询获取需定义日志传输机制（SSE 或短轮询）
5.9分析耗时统计✅ 可行服务端在 analyze 函数开始处记录 startTime = Date.now()，完成后计算 elapsed = (Date.now() - startTime) / 1000，写入日志无
5.10文档截断保护✅ 可行服务端在拼接文档内容后检查 docsContent.length > 30000，超出时 docsContent = docsContent.slice(0, 30000) + '\n\n[内容已截断]'截断阈值 30000 可配置
5.11分析错误处理✅ 可行服务端用 try-catch 包裹 ctx.llm.stream() 调用，捕获异常后返回 { error: message }，客户端在日志中显示红色错误信息需区分网络错误、模型错误、解析错误
5.12全量分析进度✅ 可行服务端遍历所有需求，循环调用 analyze 函数，每个完成后记录日志，失败时 console.error 并 continue大量需求时耗时较长，建议客户端显示进度条
5.13max-tokens 截断警告✅ 可行服务端检查 finishReason?.kind === 'max-tokens'，为真时记录警告日志 "⚠️ AI 输出被截断，建议增加 maxTokens 配置"无

调用方式

// index.js
export const inject = ['workspaceRegistry', 'webServer', 'llm'];

export function apply(ctx) {
  const llm = ctx.llm;

  async function callLLM(prompt) {
    const stream = llm.stream({
      provider: config.ai?.provider || 'deepseek',
      model: config.ai?.model || 'deepseek-chat',
      messages: [{ role: 'user', content: prompt }],
      temperature: 0.3,
      maxTokens: 4000,
    });
    let content = '';
    for await (const chunk of stream) {
      if (chunk.type === 'delta' && chunk.delta?.type === 'text') {
        content += chunk.delta.text;
      }
    }
    return content;
  }
}
